Why the deterministic controller matters (D2)

Model proposals can be malformed, incomplete or affected by issue wording. A controller can reject an invalid prerequisite, enforce the stop for issue #7, and bound repeated test and review work. A failure preserves a checkpoint. It cannot choose a different budget or next task.

Why verdict ownership matters (D7)

Immutable tests are necessary. Their outcome must also arrive through a trusted execution boundary. The supervisor observes collection, case phases and completion separately from candidate output. A local success still leaves the hosted producer and issuer to be authenticated.

Why reviewer inputs matter (D8)

The reviewer gets the issue, diff and current source, plus its own bounded test result when requested. It receives no implementation reasoning or write tools. It can locate defects and route work back to the relevant stage. A fresh context can still share the same model’s blind spots, so seeded checks would measure usefulness.

Trade-offs and experiment E1

What the controls cost

Explicit handoffs. Structured artifacts cost more context and serialization than a shared chat. They allow the controller to validate each acceptance criterion and let the reviewer form findings independently. The selected role split also incurs more coordination overhead than a single planner.

Fail-closed operation. Durable evidence needs reconciliation and can stop a valid candidate when a check is delayed. The controls make that failure visible. The current publisher has an unresolved release recovery gap when a check arrives after polling ends.

Model and budget. D6 remains deferred. The implemented Responses trial adapter targets a specific model candidate, gpt-6.1-sol. This records an implementation choice without showing account support. The broker separates secrets and records usage when a provider returns it. The ledger reserves numerical limits. A provider-enforced hard cap and secret availability remain not verified.

E2 — D9 one-use provider authorization

The unit of analysis is a concurrent invocation using the same locally reserved one-call slot. The dependent measure is whether that invocation enters the fake provider. Both comparison arms use three callers and a provider double. No billable traffic was sent.

VariantActual procedureObservation
A
Read-only grant		Run three concurrent copies with one valid grant at the same run, attempt and phase.3/3 reached the fake provider. A valid grant did not bound the number of invocations.
B
Atomic consumption		Run the corresponding three-copy test through the reference consumption service and atomic ref double.1/3 reached the fake provider. Two stopped after attempted consumption.

Change made. Consume a request-bound slot before provider HTTP, verify a fresh invocation receipt and retain the reservation on uncertain responses. The controller fails closed if the external service is unavailable.

What E2 establishes. The local protocol distinguishes reusable validation from one-use authorization under the tested concurrency schedule. GitHub ref behavior, hosted service setup, real latency, token savings and costs remain unmeasured.

Reproducibility and scope

  • E1 sources are the archived local review and the recorded Docker run 20261118T084516Z. The original TinyDB pin is shared by the experiments. The independent authority run uses f6c727d.
  • E2 sources are the archived before/after results and workflow/tests/test_consumption.py. Hosted provider configuration is deliberately disabled.
  • Historical handoff and reviewer-prompt comparison proposals were never executed. Reviewer accuracy and hosted model trade-offs cannot be inferred from these two architectural controls.
What changed across both experiments. Verification now owns the state it attests. The supervisor owns test completion. The authorization service owns consumption. That reduces dependence on output supplied by the component under evaluation.

5 · Hindsight

If starting again, specify verdict ownership and release provenance before implementing the first test gate. Require a positive case and a negative control at each trust boundary. The deployment sequence should also separate a no-spend hosted verification check from the first issue-agent trial. This would surface GitHub event and check semantics before provider setup or model tuning.

The most useful evidence came from a failure with an observable boundary. Candidate XML was insufficient even with immutable test files. A one-time budget allocation was insufficient when individual calls could reuse it. A successful CI job with a real URL was insufficient to establish deployment of the new verifier.

6 · Limitations and threats to validity

  1. Hosted validity. CI run 44280528872 used the previous base verifier. The new protected workflow/check issuer and complete issue-to-review path were not verified. The latest security patch remains local and uncommitted.
  2. Experimental controls. E1 changes both architecture and the forged-result mechanism across arms. E2 uses service/ref/provider doubles. Neither estimates production risk or provider behavior.
  3. Small sample and oracle conflict. The five tasks are from a single repository. #4 has a pinned regression conflict and #7 intentionally lacks a product behavior oracle. Reference tests are not independent hosted agent fixes.
  4. Reviewer evaluation. Five local seeded diff examples are available. Hosted seeded reviews were not executed. No true/false-positive or missed-defect count is available. A fresh context can still share model bias.
  5. Operational dependencies. Dispatch authorization, issuer provenance, per-PR meaning of commit-scoped checks, and late-release recovery remain open. Docker and dependency trust also limit inference from one host.
  6. Spend and audit. No paid hosted model usage was observed. Coordinator tokens, account secret availability and provider hard-cap enforcement were not verified. Both production configurations remain disabled.
