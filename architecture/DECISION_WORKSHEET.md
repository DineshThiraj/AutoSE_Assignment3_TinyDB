## D1: Splitting the work

**Problem.** The six stages need different context and authority; release is an API operation, not a reasoning task.

**Recommendation to assess.** Use four fresh-context reasoning roles: requirements, design, implement/test author, reviewer. Deterministic controller performs testing and release; stage 4 includes model test authoring followed by trusted execution checks.

**Alternatives and tradeoffs.** One persistent general agent is cheaper to orchestrate and retains context, but concentrates authority and self-review bias. Six role-specific agents simplify stage ownership but add handoff loss and API overhead.

**Security and authority.** Reasoning roles receive no push token or arbitrary shell. Implementer may propose edits only in tinydb/ and tests/; reviewer only reads and requests fixed test execution.

**Cost, complexity and failure behavior.** Four prompts plus deterministic stages are moderate complexity. Fresh contexts repeat source tokens; shared implement/test context saves some tokens. Failed reasoning or malformed output stops the stage with an artifact.

**Evidence needed.** Compare task correctness, handoff failures, tokens and wall time before claiming the role count improves outcomes.

## D2: Control flow

**Problem.** Tests and reviewer feedback require loops, while workflow execution must remain bounded and explainable.

**Recommendation to assess.** A deterministic state machine selects transitions; explicit Actions jobs separate credential domains. Review returns a validated target stage (requirements/design/implementation/testing); controller, not model, enforces routing and reruns downstream gates.

**Alternatives and tradeoffs.** A model planner adapts freely but can skip gates and consume unbounded calls. Pure linear jobs are simpler but cannot implement the mandated feedback path. Dynamic cross-workflow recursion is harder to deduplicate.

**Security and authority.** Only trusted controller code from reviewed base may schedule stages. Never execute scripts generated by the issue or patch. All next-state values validated against a fixed graph.

**Cost, complexity and failure behavior.** Propose two total review rounds and at most two implementation/test attempts per review cycle, with a global call/token/time budget. Exhaustion stops; it is not approval. Job count is higher than one shared runner.

**Evidence needed.** Unit-test illegal transitions, reviewer target routing, budget exhaustion and no third review. Compare traces of one actual failure-and-repair cycle.

## D3: Handoffs

**Problem.** Context must preserve testable intent without revealing hidden tests, secrets or implementer reasoning to the reviewer.

**Recommendation to assess.** Save full spec and design plus structured metadata for implementation. Reviewer receives only issue, diff, latest code snapshot and its own trusted prompt. Stage 1 also preserves all three original A1 artifacts.

**Alternatives and tradeoffs.** Summaries save tokens but can omit constraints. Full conversations preserve detail but leak implementation reasoning and amplify injection. Repository-global AGENTS files could change role instructions unexpectedly.

**Security and authority.** Build explicit input manifests with SHA-256, file lists and bounded sizes; reject symlinks/path traversal. Keep run traces, decisions about seeded defects and hidden tests out of reviewer mounts.

**Cost, complexity and failure behavior.** Repeated full files cost more tokens. Fail on truncated or missing required input; never silently downgrade to a summary. Unknown critical requirements stop instead of invented approval.

**Evidence needed.** Experiment candidate: complete spec/design versus structured summary for implementation only. Keep model, task, source, prompt policy and test oracle fixed. Inspect criterion omissions.

## D4: State

**Problem.** Restarts and repeated label/comment events must not double-spend or overwrite evidence.

**Recommendation to assess.** Unique attempt IDs based on repository, issue, event/run ID and run attempt; immutable per-attempt artifacts with hashes and append-only transitions. Persistent PR/run index deduplicates completed events; new authorized reruns are distinct attempts.

**Alternatives and tradeoffs.** Branch files are durable but can contaminate reviewer inputs. Comments are visible but editable and poor for structured state. Actions cache can be evicted and is not an authoritative ledger.

**Security and authority.** Treat downloaded artifacts and PR indexes as untrusted; validate run origin, schema, expected base/head SHA and hashes. No workspace cache carries credentials or model context.

**Cost, complexity and failure behavior.** Retention requires exporting essential artifacts into results/ or durable owned storage. Interrupted attempts require reconciliation against remote refs/PRs before release; cannot promise exactly-once external API calls without reconciliation.

**Evidence needed.** Crash before/after branch push and PR creation; replay the same event; check one PR and distinct intact evidence. Document configured artifact retention.

## D5: Tools

**Problem.** Agents need repository context but should not execute arbitrary issue commands or access credentials.

**Recommendation to assess.** A trusted model broker has provider key and fixed read/edit-proposal tools; it never imports or executes target code. Disposable no-secret jobs apply validated changes and run fixed compile/pytest commands. A separate trusted release publisher alone has fork-scoped write token.

**Alternatives and tradeoffs.** One key-bearing shell agent is easy to build but allows generated code to read/exfiltrate credentials. A general MCP shell expands attack surface. Full VM isolation is strong but more setup than a small fixed-command runner.

**Security and authority.** Disable persisted checkout credentials. Trusted orchestration runs from base SHA outside patched code. Patch paths restricted; reject .github/, workflow/, Git config, symlinks and special files. Execution has no provider key, no write token and no access to broker process.

**Cost, complexity and failure behavior.** Artifact transfer adds latency and validation code. Read tools enforce byte limits and approved paths. Invalid patches fail closed; test processes get timeouts/resource limits. Read-only token on runner is still a credential and must be minimized.

**Evidence needed.** Adversarial patch attempts workflow edit, traversal, symlink replacement, test-hook secret reads and upstream remote substitution. Verify publisher never executes generated code.

## D6: Models

**Problem.** Trials must use a supported model and known cost/usage semantics, not an inferred local-login capability.

**Recommendation to assess.** Prefer exact gpt-6.1-sol at medium for repeated reasoning trials as requested; keep reviewer fresh-context with the same model initially to control diversity. Provider and hosted API support remain unresolved; no final model decision until verified.

**Alternatives and tradeoffs.** Different reviewer model may reduce correlated errors but confounds independence and cost comparisons. Local ChatGPT-authenticated CLI is not evidence of an available hosted API credential. Smaller models reduce cost but may fail architecture tasks.

**Security and authority.** Broker alone sees API key. User establishes hard provider cap and repository secret. Model outputs and provider errors are untrusted and must not echo headers/keys.

**Cost, complexity and failure behavior.** Need current official provider model identifier, reasoning option, token usage and prices. Proposed bounded response sizes and call count are secondary guards, not substitutes for provider hard cap. No paid smoke or fallback without authorization.

**Evidence needed.** Before freezing trials, perform authorized nonexperimental hosted smoke, record exact model/effort/provider/SDK and usage fields. Stop if requested model unavailable; student chooses any documented alternative.

## D7: Checks

**Problem.** A successful model response cannot establish semantic correctness or CI success.

**Recommendation to assess.** Controller validates schema and AC structure; a narrow validation reasoning pass assesses testability and file/function grounding. Deterministic compile and full pytest determine build/test gates; verify baseline JUnit identifiers and one mapped new test per AC. CI gate requires actual success at exact PR head SHA.

**Alternatives and tradeoffs.** LLM-only gates can approve broken code. Pure string checks cannot judge semantic testability. Only agent-authored tests permit weakened tests to conceal regressions.

**Security and authority.** Restore pristine original tests during evaluation; reject deletion/weakening of baseline tests. Hidden tests run later outside agents. Release verifies repository, branch, SHA, PR open state, and required CI checks with pagination.

**Cost, complexity and failure behavior.** Additional validation calls increase cost and can still err. Missing JUnit cases, collection error, skipped expected checks or stale CI cannot pass. Human/course evaluation remains stronger than claimed automatic proof.

**Evidence needed.** Plant self-reported success, xfail/skip, missing tests, non-asserting tests, compile failure and stale green CI. Measure gate false acceptance and rejection.

## D8: Reviewer independence

**Problem.** A separate name or prompt alone cannot prevent shared-context agreement or permission escalation.

**Recommendation to assess.** Fresh broker request and sanitized source snapshot with issue/diff only; separate reviewer prompt asks for evidence-backed findings and stage routing. Reviewer has no edit/push tools. A trusted publisher posts its structured verdict without exposing write credentials to model or code execution.

**Alternatives and tradeoffs.** Same conversation is cheap but violates independence. Separate model adds diversity but does not itself remove shared context. A separate job with secrets still exposed to code is insufficient.

**Security and authority.** Do not checkout full implementation branch metadata/docs containing traces into review context. Pin reviewed PR SHA, remove credential persistence, and deny review access to hidden ground truth. Publisher validates verdict, paths and line references.

**Cost, complexity and failure behavior.** Posting with github-actions bot may encounter platform self-review restrictions; verify in first authorized slice. If actual approval cannot be posted, record blocker and use a justified separate trusted GitHub identity with explicit authorization; never impersonate student approval.

**Evidence needed.** Five seeded PRs with privately frozen labels; score true detections, misses and false positives. Prompt variants: terse correctness review versus evidence/category checklist, holding inputs/model fixed. Neither positive review nor round exhaustion proves correctness.

## D9: Safety and failures

**Problem.** Authorized triggers do not make issue content, generated patches or dependency hooks trustworthy.

**Recommendation to assess.** Deny arbitrary commands; bound calls/tokens/response sizes/test timeouts and review rounds; preflight hard cap; upload failure evidence with always-run finalization. Fail closed on absent authorization, credentials, usage or check evidence.

**Alternatives and tradeoffs.** Prompt-only injection instructions do not enforce isolation. Unlimited retries hide failures and waste spend. Soft monthly budget alerts do not meet a hard spending-limit requirement.

**Security and authority.** No pull_request_target execution of PR code; no model keys in test/review execution. Provider broker accepts only fixed operations; no shell interpolation of issue/title/branch/model output. Fork-only allowlist checked immediately before each mutation.

**Cost, complexity and failure behavior.** Provisional limits: 40-minute whole run, 5-minute test process, 15-minute reasoning-stage ceiling, two review rounds, two implementation attempts per cycle, 24 total broker calls, token cap chosen after pricing/cap review. Provider call timeout and cancellation can still incur charges.

**Evidence needed.** Failure cases: unauthorized actor, provider timeout/malformed output, failing tests, request-changes, exhausted budget, interrupted publisher and duplicate event. Preserve all valid failures and unavailable usage honestly.

## D10: Triggers

**Problem.** Anyone may write issues; multiple triggers can race and PR comments must not accidentally start unrelated work.

**Recommendation to assess.** Start on autose label on an issue or exact /autose comment on an issue; use API collaborator permission check for write/maintain/admin plus expected repository owner. Initially reject PR comments and bot actors; assignment sketch gives PR comments only as an example.

**Alternatives and tradeoffs.** Label-only is simpler but less ergonomic. Author association alone is coarse. workflow_dispatch is useful for explicitly controlled experiments but cannot replace the required issue entry path.

**Security and authority.** Concurrency group per repository/issue with cancel-in-progress false; durable event deduplication still required. A re-run must recheck authorization and fixed source state. No issue text flows directly into shell expressions.

**Cost, complexity and failure behavior.** Queued jobs and reconciliation add latency. Permission API failure stops safely. Freeze issue text/hash at admission so edited issues cannot silently change a paired trial.

**Evidence needed.** Trigger tests: untrusted outsider, legitimate maintainer, lookalike comment, comment on PR, replayed event, bot feedback and simultaneous label/comment. Verify no recursive model runs.
